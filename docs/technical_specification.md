# وثيقة المواصفات التقنية والهندسية الشاملة (Enterprise Technical & Architectural Specification)

تستعرض هذه الوثيقة المواصفات الفنية والهندسية المفصلة لتصميم، وتطوير، ونشر، وتشغيل المنصة الشاملة (العميل والأدمن)، مع التركيز على الأداء العالي، أمن البيانات، سرعة استجابة الذكاء الاصطناعي، تكامل الخرائط الدقيق، والتزامن اللحظي عبر العملاء.

---

## 1. فصل واجهة العميل عن واجهة الأدمن (Client vs. Admin Portal Architecture)

لضمان أعلى معايير الأمان، وقابلية التوسع (Scalability)، وعزل الصلاحيات، يتم اعتماد بنية هجينة ومتطورة مفصولة المنطق:

### أ. البنية التحتية والواجهات (Frontend & Architecture)
* **بوابة العميل (Client Portal / PWA):**
  * مخصصة للمستخدمين النهائيين والعملاء لتصفح المنتجات، تقديم الطلبات، استخدام مساعد الذكاء الاصطناعي والميزات الطبية.
  * مبنية باستخدام React + Vite مع Service Workers لدعم العمل دون اتصال (Offline-first PWA).
  * تركز على سرعة التحميل (Core Web Vitals متقدمة، LCP < 1.2s)، واجهات مستخدم سلسة وتصميم متجاوب بالكامل.
* **بوابة الأدمن (Admin Portal):**
  * معزولة تماماً في مسار آمن ورابط مخصص (`/admin/...`) مع التحقق من الهوية عبر جلسات مشفرة وRole-Based Access Control (RBAC).
  * مصممة للتحكم الشامل بلوحات القيادة، إدارة المستخدمين، مراجعة الطلبات، مراقبة الأنظمة، وإدارة إعدادات النظام.

### ب. واجهات برمجة التطبيقات (APIs & Micro-routing)
* **APIs العميل (`/api/v1/client/...`):**
  * تركز على معدلات طلبات مرتفعة (Rate Limiting مخصص للعملاء)، وتشفير عالي للبيانات الحساسة.
* **APIs الأدمن (`/api/v1/admin/...`):**
  * محمية بطبقات تحقق إضافية (MFA / Admin Tokens)، وتسجيل تدقيقي (Audit Logs) لجميع عمليات الكتابة والتعديل (CUD operations).

### ج. نماذج الصلاحيات والأدوار (RBAC & Permissions)
* **المستويات:**
  1. `Super Admin`: صلاحيات مطلقة على النظام وإدارة الـ Feature Flags والبنية التحتية.
  2. `Operations Manager`: إدارة الطلبات، المخزون، والتقارير.
  3. `Support / Moderator`: إدارة الشكاوى، دعم العملاء، والمحتوى المؤقت.
  4. `Verified Client / Pharmacist`: الوصول للمميزات الطبية المتخصصة وعروض الولاء.
* **التنفيذ التقني:** تخزين الـ Claims داخل JWT Tokens ومطابقتها عبر Firebase Custom Claims أو Cloud SQL Row-Level Security (RLS).

## 2. متطلبات واجهة الأدمن المتقدمة (Advanced Admin Dashboard)

توفر لوحة التحكم للأدمن الأدوات التالية للتحكم والرقابة:

* **إدارة المحتوى والمستخدمين:**
  * جداول تفاعلية مع ميزات البحث، الفلترة المتقدمة، التصدير والاستيراد (Excel/CSV)، وحظر/تفعيل الحسابات لحظياً.
* **مراقبة الأداء والـ Logs:**
  * لوحة مراقبة حية تعرض استهلاك الخوادم، معدلات أخطاء الـ API، أزمنة استجابة قواعد البيانات، وتدفق الـ System Logs مع إمكانية التصفية بحسب الخطورة (Error, Warning, Info).
* **إدارة الذكاء الاصطناعي وإعدادات النماذج:**
  * واجهة لتعديل درجة الحرارة (Temperature)، اختيار النماذج (مثل `gemini-2.5-flash` أو النماذج الأحدث)، وتعديل الـ System Prompts بدون الحاجة لإعادة نشر الكود.
* **نظام ميزات النظام (Feature Flags):**
  * مفاتيح تحكم فورية (Toggle Switches) لتفعيل أو إيقاف ميزات معينة (مثل: مساعد الذكاء الاصطناعي، شحن الفلاش، نظام الألعاب، دفع البوابة الإلكترونية) لجميع العملاء أو لشرائح محددة (Canary Rollout).

## 3. استراتيجية تسريع استجابات الذكاء الاصطناعي (AI Response Acceleration)

لتحقيق زمن استجابة دون الثانية (< 800ms) لطلبات الذكاء الاصطناعي:

* **التخزين المؤقت الذكي (Semantic Caching):**
  * تخزين الأسئلة الشائعة وإجابات النماذج في Redis / Firestore Cache مع مطابقة التشابه الدلالي (Semantic Similarity) لتجنب استدعاء نموذج الذكاء الاصطناعي للمتطلبات المتكررة.
* **تحسين حجم وحمولات الطلبات (Token Optimization):**
  * تقليم السياق (Context Pruning)، وضغط الرسائل السابقة للدردشة، واستخدام System Instructions مختصرة ومركزة لتقليل عدد الـ Input Tokens المستهلكة.
* **استدلال الحافة والنماذج خفيفة الوزن (Edge & Low-Latency Models):**
  * الاعتماد على نماذج فائقة السرعة مثل `gemini-2.5-flash` أو الإصدارات المحدثة للاستجابات الفورية، مع تحويل العمليات الحسابية الخفيفة إلى طبقة الـ Edge.
* **معالجة الدفعات (Batch Processing) وقوائم الأولوية (Priority Queues):**
  * جدولة طلبات التحليل غير الفورية (مثل تقارير الأداء اليومية) في طوابير معالجة خلفية (Background Workers)، مع إعطاء أولوية قصوى لطلبات المستخدمين المباشرة (Critical Path).
* **التوسع التلقائي (Autoscaling):**
  * ضبط قواعد التوسع التلقائي لخوادم الـ API الوسيطة (Serverless / Cloud Run) بناءً على معدل الطلبات المتزامن (Concurrency).

## 4. إصلاح وتحسين منظومة الخرائط والموقع (Map & Geocoding Reliability)

* **اختيار المزود الأمثل:**
  * الاعتماد الأساسي على Google Maps Platform (JavaScript API, Places API, Geocoding API) لضمان الدقة العالمية والتغطية المحلية الشاملة.
* **إدارة مفاتيح API والأمان:**
  * تقييد مفاتيح الخرائط بـ HTTP Referrers وIP Restrictions، وتمرير الطلبات الحساسة عبر خادم الـ Backend (API Proxy) لإخفاء المفاتيح السرية وحمايتها من السرقة.
* **تحسين الـ Geocoding والـ Reverse-Geocoding:**
  * دمج آليات تصحيح العناوين التلقائي، والبحث التنبؤي (Autocomplete)، مع تخزين مؤقت (Client/Server Cache) لإحداثيات العناوين المتكررة لتقليل استهلاك الـ Quotas.
* **التخزين المؤقت للـ Tiles والخرائط:**
  * استخدام Service Workers لتخزين عناصر الـ Map Tiles مؤقتاً لتمكين التصفح السريع وتقليل استهلاك البيانات للعملاء ذوي الاتصال الضعيف.
* **آليات البديل عند انقطاع الخدمة (Fallback Mechanisms):**
  * في حال تعذر الاتصال بخدمة الخرائط الحية، يتم التحويل تلقائياً إلى خريطة تفاعلية محلية خفيفة (مثل Leaflet / OpenStreetMap مدمجة) مع إدخال العنوان يدوياً.

## 5. تزامن التحديثات عبر كافة العملاء والنشر الآمن (Real-Time Sync & CI/CD)

* **بنية التحديثات اللحظية (Real-Time Sync):**
  * استخدام WebSockets / Firestore Real-time Listeners لبث التحديثات الفورية (تحديثات الطلبات، تغيير الأسعار، تنبيهات المخزون) لجميع العملاء المتصلين دون الحاجة لإعادة تحميل الصفحة.
* **استراتيجية النشر (Blue/Green & Canary Deployments):**
  * استخدام مسارات CI/CD متقدمة عبر GitHub Actions لاختبار الكود تلقائياً (Unit & Integration Tests)، ثم نشره بنظام Canary (إرسال 10% من حركة المرور للإصدار الجديد ثم التوسع التدريجي) أو Blue/Green للتبديل الفوري دون انقطاع الخدمة (Zero Downtime).
* **إصدارات واجهات برمجة التطبيقات (Versioned APIs):**
  * اعتماد ترقيم الـ APIs (مثل `/api/v1/...`, `/api/v2/...`) لضمان عدم انكسار التطبيقات الحالية عند تحديث الخدمات الخلفية.
* **ترحيل قواعد البيانات (Safe Database Migrations):**
  * تنفيذ قواعد البيانات بنهج Backward-Compatible migrations لضمان عدم توقف النظام أثناء تحديث الهياكل (Schemas).
* **آلية التراجع السريع (Rollback Strategy):**
  * مراقبة أخطاء الإنتاج بعد كل عملية نشر؛ وفي حال تجاوز معدل الأخطاء الحد المسموح، يتم التراجع تلقائياً للإصدار المستقر السابق خلال ثوانٍ.

## 6. مراقبة الأداء، مؤشرات النجاح، ومستويات الخدمة (Monitoring, SLOs & KPIs)

* **مؤشرات الأداء الرئيسية (KPIs):**
  * **زمن استجابة الذكاء الاصطناعي (AI Latency):** متوسط وقت الاستجابة < 800ms.
  * **معدل أخطاء الخرائط (Map Error Rate):** أقل من 0.1% من إجمالي الطلبات.
  * **وقت التزامن عبر العملاء (Sync Latency):** أقل من 300ms لتحديثات الـ WebSocket.
  * **معدل توافر الخدمة (Uptime SLO):** 99.95%.
* **نظام التنبيه والمراقبة (Alerting & Observability):**
  * ربط الأنظمة بأدوات مراقبة حية (مثل Sentry للأخطاء، Google Cloud Monitoring للأداء، وUptime Checkers).
  * إرسال تنبيهات فورية عبر قنوات العمل (Slack / Telegram / SMS) لفرق الهندسة فور تجاوز أي مؤشر للحدود الحرجة (مثل ارتفاع أخطاء 5xx أو انخفاض الاستجابة).
